# 原則と落とし穴

この文書は、ui-video-builder で動画の仕組みを生成するエージェントが読む。読み終えると、生成する仕組みが守るべき原則と、先に踏んだ落とし穴の避け方が分かる。生成する動画のスキルにも、ここから当てはまるものを書き写す。

原則は、破ったときの被害が大きい順に並べる。どれも、実際に動画を作って踏んだ失敗から書いている。

## 1. 同じコマは、何度撮っても同じ絵になる

一番大事な原則である。同じコマが同じ絵にならないと、字幕を1行直しただけでほかのコマまで変わり、エージェントは「直した所だけが変わったか」を確かめられない。合格試験の「同じコマ」は、これを確かめる。

同じ絵にならない原因と直し方は、次のとおり。上から順に、踏みやすい。

| 原因 | 症状 | 直し方 |
| --- | --- | --- |
| 動画の部品が、時計、乱数、タイマー、通信を使う | 数値や並びが撮るたびに違う | 動画の部品では`Date.now()`、`Math.random()`、`setTimeout`、通信を使わない。値はコマの番号から計算する |
| アプリが乱数を使う | 入力欄の例文など、アプリが選ぶ文や絵が撮るたびに違う | 画面の作り方では、ページに差し込む処理で`Math.random`を、呼んだ場所ごとに決まった値を返すものに替える。1つの種から順に値を出す作りは、フレームワークの開発用の道具も乱数を呼び、呼ぶ順がページを開くたびに変わって崩れる(Next.js の開発サーバーで起きた)。同じ場所が呼ばれる回数も変わる |
| 入力欄のカーソルが点滅する | 打った直後のコマで、入力欄の縁の数ピクセルが違う | カーソルの点滅はブラウザの中の時計で進み、偽の時計で止まらない。Playwright の`caret: "hide"`は撮る間しか隠さない。ページ全体に`caret-color: transparent`をずっと当てる |
| フレームワークの開発用の表示が映る | Next.js の「Issue」の印や、Vite のエラーの表示が映る | 撮るときは隠す。開発用の表示の中身はアプリの状態で変わり、絵を揺らす元にもなる |
| CSSのアニメーションが、ブラウザの時計で進む | グラフの伸びや読み込みの輪の位置が違う | ページの時計を Playwright の偽の時計に替え、1コマごとに1/fps秒だけ進める。毎コマ`document.getAnimations()`を止め、動きが始まってからの偽の時計の経過に合わせる |
| SVGのSMILのアニメーションは、`getAnimations()`に入らず、Playwrightの`animations: "disabled"`でも止まらない | スピナーの部分だけ違う | 毎コマ、すべての`svg`で`pauseAnimations()`と`setCurrentTime(コマ/fps)`を呼ぶ |
| 遅延読み込みの部品(`React.lazy`など)が、読み込みの前は代わりの表示を出す | Markdownが素の文字のまま写る | 本番の描画の前に、見えない場所で一度描いて読み込みを済ませる。描き終えたことを、代わりの表示との違いで確かめる |
| フォントの読み込みの前に撮る | 文字の形や幅が違う | `document.fonts.ready`を待ってから撮り始める |
| 読み込みの途中で撮る | 開いた直後のコマだけ、一覧が空のことがある | 部品の作り方では、描き終えたら`window.__frameReady`を立て、それを待つ。画面の作り方では、通信が十分な間静かになるまで待つ。60ミリ秒の静けさを10回続けて確かめた |
| ブラウザが前のコマで描いた絵を使い回す | ページの要素の位置と値は同じなのに、縁の数ピクセルだけが違う。場面の始めから進めたときだけ違い、そのコマで直接開くと一致する | 撮らないコマでも、1ピクセル四方のスクリーンショットを撮って毎コマ1回描かせる。撮らないコマの間に実際に何回描いたかで縁のぼかしが変わるので、描いた履歴を毎回同じにする |

描いた履歴を毎回同じにしても、文字の縁の数ピクセルが、まれに2通りに分かれることがあった。部分の描き直し(変わった所だけを描き直す仕組み)を止めて、chromium を`--disable-partial-raster`で起動すると直った。見本は両方を入れている。

まれにしか起きない揺れは、同じコマを2回撮るだけでは見逃す。合格試験は3回撮って比べる。原因を絞るときは、同じコマを6回以上撮って、違う範囲を出す(`scripts/repeat.mjs`)。

表の最後の2行は、見つけるのが一番難しかった。GPUを止める、撮る前に待つ、描き終えてから画面を作る設定は、どれも効かなかった。原因を絞るときは、そのコマで直接ページを開いて撮り、一致するかを見る。一致するなら、描いた履歴が原因である。

## 2. 数値と文は、アプリから持ってくる

部品が本物でも、渡す値を手で書けば、動画は作り話になる。

- 金額や指標は、動画のために手で書かない。部品の作り方では、アプリと同じ関数で計算する。画面の作り方では、録った通信の応答を使う
- AIの応答の文は、実際の応答を写す。画面からはコピーしない。画面の文字は描いた後の文字で、記号や改行が元と違う。データベースか、録った通信から取る
- 尺に収めるため、応答は文の単位で省くことだけを許す。言い換え、書き足し、文の途中での切り取りはしない。残した文が元の応答の部分列であることを、単体テストで確かめる
- 動画に映すデータは架空のものにする。実在の人、会社、物件、住所と結びつく値を使わない
- 地名や名前を映す前に替えるときは、元の値は持ったまま、映す直前にだけ替える。替えると字数が変わり、文字が流れて出る長さがずれるためである

## 3. 利用者のアプリのコードは、なるべく変えない

- 画面の作り方は、アプリのコードを変えずに撮れる。既定はこちらにする
- 部品の作り方で、部品にデータを外から渡せないときも、まず場面の側で組めないかを探す。部品に動画のための分かれ道を足すのは最後の手段にする。足すときは、省略できる引数にし、省略したときの動きを変えない。利用者に理由を示して確かめる
- アプリに無い画面、行、札、一覧を、アプリの部品の見た目で作らない。「スマホに実際にある?」と指摘された。寄る、切り出す、アプリの画面の中で送る、はよい

## 4. 録った通信に、秘密を残さない

- 録るときに、鍵、トークン、クッキー、個人情報らしい値を伏せる
- 録ったファイルは、既定で git に入れない。`.gitignore`に入れる
- 録るのは、デモ用の利用者の、架空のデータだけにする
- 本物のAIに送る、課金される呼び出しは、送る前に利用者に確かめる

## 5. 動画のコードは、本番のビルドに入れない

- 動画の入口は、本番と別のビルドの設定から組む
- 本番のビルドの出力に動画のコードが入っていないことを、文字列の検索で確かめる

## 6. 録った応答を返す仕組みで要ること

画面の作り方で、録った通信を返すときに要ったこと。

- **UUIDの対応表。** 呼び出しの`id`だけでなく、会話の`threadId`のような値も、ブラウザが毎回新しく作る。録った応答を選ぶときは、引数のUUIDを伏せて形で対応を取る。対応したUUIDの組を表に積み、返す応答の中の録ったUUIDを、今のページのUUIDに書き換える
- **操作の前と後の時期。** 同じ呼び出しでも、操作の前と後で応答が違う。操作の呼び出しが届いた時点で時期を切り替え、時期ごとに、同じ呼び出しが来た順に録った応答を返す
- **流して出す応答。** 応答の差分を手元に止めておき、決めたコマで1つずつ返す。録った応答が一度に全文で届いていたら、録った全文を分けて出す。文は録ったままにし、出る速さだけを台本で決める
- **開いた直後に始まる動き。** 一覧が下から出てくるような、ページを開いた直後に始まる動きは、0コマ目から始まると最初のコマが空に見える。0コマ目の前に撮らないコマを進めて、動きを済ませておく
- **画像。** HTTPの応答は、文字列ではなくバイト列で録る。画像が壊れる
- **WebSocket。** Playwrightの`routeWebSocket`で、バックエンドにつながずに応答する。開発サーバーの自動再読み込みの通信は、差し替えない

## 7. 見せ方

### カメラ

- アプリの画面は1920×1080で描くと、スマートフォンでは文字が読めない。画面の中の矩形を指定して寄るカメラを作る
- 寄るときは、数コマで速く寄せて止める。ゆっくり寄ると、その間どこを見ればよいか分からない。止まった所が、見てほしい所だと伝わる
- 寄る先は、要素の矩形から決める。座標を手で書くと、字幕の帯に重なった
- 画面の端の要素に寄るときは、ページの外を映さない。見本のカメラは、映す範囲がページより狭いときに端で止める
- 横いっぱいの要素(見出しの帯など)は、矩形から拡大率を決めると拡大しない。拡大率を直に決める。左右の端に分かれた要素の片側を見せるときは、寄る中心を端にそろえる
- 寄せたまま操作すると、変わる所が画面の外になることがある。変わる所が映る寄り先にしてから操作する
- 入力欄がページの下の端にある画面は、入力欄に寄っても、ページの外を映さないよう端で止まり、入力欄が画面の下に寄る。入力欄と、その上の会話の終わりをまとめて寄る先にする
- 字幕の帯の高さを決めて、カメラの計算と合わせる。帯の文字の行の高さを決めないと、帯が思ったより高くなり、アプリの上の部分を隠した
- 画面の全体を見せるときも、字幕の帯の下に収める。画面の全体の矩形のまま映すと、帯がアプリの上の部分を隠す
- 縦に長い要素(画面の高さいっぱいの会話の欄など)にそのまま寄ると、拡大せずにかえって縮む。要素の上の部分に絞って寄る

### 字幕と操作の時機

- 字幕は、操作の前に出す。操作と同時に字幕が替わると、何が起きたかを読む前に画面が変わる
- 録った応答はすぐ返るので、操作したコマのうちに画面が変わり、「更新中」のような途中の表示が映らない。見せたいときは、応答を決めたコマ数だけ遅らせて返す(場面の設定の`responseDelayFrames`)

### 強調

- 赤い丸、取り消し線、ペンで囲む線、早送りの札を、手書き風に重ねる
- 強調の印は、描き終えてから1.5秒以上映し続ける
- 枠と丸の線は、文字、ボタン、アイコンに重ねない。文の途中の語を丸で囲むと、前後の文字に線がかかる。文の1行や欄を枠で囲む

### 断りと注記

- 「開発中の画面です」や法務の注記は、本編より目立たせない。同じ大きさで右下にまとめる。画面の中央に大きく出したら、目立ちすぎると言われた

### 縦型

- 横型の絵を切り抜くだけでは、余白や読み込み中の画面が絵の大半を占め、ほとんど何も映らないコマが続く。「これでは飛ばされる」と言われた。縦型は、別の組み方として作り直す
- 縦長のページでアプリを開くと、アプリはスマートフォンの並びで描き直され、見せたい画面と変わる。アプリはパソコンの大きさのまま描き、その絵を縦の台紙の窓に置く。字幕は台紙に描く。窓の縦横の比は、アプリを描く大きさの比と同じにする
- 窓は、縦の台紙の上のほうに置く。窓の下端は、1080×1920 の台紙で 1260px までにする。下の660pxは、TikTok の説明文とコメントに隠れる
- 題名、場面のつなぎ、結論、ロゴのように、アプリの画面を映さない場面は、縦の台紙の全体に描く
- 字幕、見出し、注記、ロゴは、TikTokの安全域に置く。値は合格試験と同じで、1080×1920で上240px、下660px、左右120pxを空け、上から840pxより下では右端から180pxを使わない
- 文字は、いちばん長い行が安全域の幅いっぱいに近づく大きさにし、字幕の箱の縦の中ほどに置く。「上すぎる・小さすぎる」と指摘された
- 見出しの印は行ごとに付ける。複数の行をまとめた枠で測ると、狭い行の横までボタンの列にかかって見える
- 背景は、上の字幕の後ろまで縦の台紙の全体に描く
- 縦型の「空のコマ」は、台紙の窓の中だけで数える。台紙の地の色を含めると必ず空と数える
- 余白の多いアプリは、寄って文字を読ませると窓の中が白くなり、「空のコマ」に数えられる。アプリを描く大きさ、特に縦を小さくして、余白そのものを縮める(800×500 で描いて通った例がある)。それでも余白が残る場面は、寄る先を、文字の詰まった所に絞る。地の色の上に大きな文字だけを出す場面は、数えない場面に入れる
- 縦型は、先に `--check blank` だけを流して、アプリを描く大きさとカメラを決めてから、全部の確かめに進む

### 絵コンテ

- 最初の5秒で、見る人を引きつけるか、何の動画かを明かす
- 実在のサイトやアプリの画面に似せた絵を、大写しにしない。広告の審査で「誤解を招く広告のデザイン」として止まった。アプリの画面のメニューを3.5倍に寄せた版も止まり、1.5倍に弱めて窓の端と背景が見える大きさにした
- 「丸投げできる」のような、少ない手間で成果が出ると約束する言い回しを、結論や題名に使わない。広告の審査で「信頼できない文言」として止まった。試した感想や問いかけの形にする
- 文字に装飾を足さない

### 写真の素材

- 商用に無料で使え、クレジットの表示を求めない許諾の写真を使う。取得元のURLと許諾を、素材の隣の`SOURCES.md`に書く
- 車のナンバー、看板、表札、電話番号のように、特定できる文字はぼかす
- 写真の国や地域を、動画の対象に合わせる

## 8. ナレーション(任意)

ElevenLabs で作る。鍵は利用者が用意する。

- 台本の発話ごとに音声を作り、尺を測ってJSONに書き出す。場面の中で次の操作が始まるコマは、この尺から計算する。発話を変えて作り直すと、時刻も自動でついてくる
- 音声の生成は課金される。作り直す前に、利用者に確かめる。作った音声は上書きせず、元の版を残す
- 漢字の読みの誤りは、読み上げ用の文を仮名で書いて直す
- アクセントの誤りは、仮名にしても直らないことがある。最後の手段として、音声の一部の高さの曲線を、Praat(Python の parselmouth)で書き換える

## 9. 動画のスキルを育てる

- 利用者やレビューの指摘で直したことは、その場で、生成した動画のスキルの決まりか落とし穴に書き足す。日付と理由を添える。同じ指摘を2度受けないためである
- 決まりのうち、機械で判定できるものは、自動のチェックに移す。判断が要るもの、たとえば何を強調するかは、スキルに残す
