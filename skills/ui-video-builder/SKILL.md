# ui-video-builder — 動画を作る仕組みを、このリポジトリに生成する

このスキルは、アプリの実際の画面を使って操作説明や宣伝の動画を作る仕組みを、利用者のリポジトリに生成するエージェントが読む。読み終えると、リポジトリを調べて作り方を選び、エンジンと、そのリポジトリ専用の動画のスキルを生成し、合格試験で確かめるところまで進められる。

生成する仕組みは、次のことができるものにする。

> アプリが変わっても作り直せる操作説明の動画を、エージェントが作り、自動のチェックで確かめる

画面は録画しない。録画は、AIの応答の文、待ち時間、マウスのぶれが撮るたびに変わり、字幕を1行直すだけで撮り直しになる。代わりに、同じコマからは必ず同じ絵が出る仕組みで、1コマずつ撮る。

## このスキルの中身

| ファイル | いつ読むか |
| --- | --- |
| `references/principles.md` | 生成を始める前に必ず読む。守る原則と、先に踏んだ落とし穴 |
| `references/acceptance.md` | 撮る関数のファイルを書く前に読む。合格試験の約束 |
| `references/samples/screen/` | 画面の作り方を選んだら、ここから書き写す |
| `references/samples/component/` | 部品の作り方を選んだら、ここから書き写す |
| `references/video-skill-template.md` | 動画のスキルを生成するときに読む。ひな形 |
| `scripts/check.mjs` | 合格試験。生成させず、このまま使う。中身を書き換えない |
| `scripts/repeat.mjs` | 揺れの原因を絞る道具。同じコマを何回も撮り、違う範囲を出す |

見本の画面の作り方には、記事や広告の動画で使う部品が入っている。強調の印(赤い丸、枠、取り消し線、蛍光ペン)、早送りの札、マウスのカーソルとクリックの波紋、題名やロゴの札、断りと法務の注記、ナレーション(ElevenLabs)、効果音、字幕の SRT である。どれも場面の設定に書くだけで描かれる。形は `references/samples/screen/shoot.mjs` の冒頭と `overlay.js` の6節にある。部品の作り方でも、`overlay.js` を部品の作り方の見本と同じ置き場に写し、動画の構成に `overlay: { captions, marks, cursor, cards, notes }` を書けば、同じ部品が使える。見本の `check-adapter.mjs` が `overlay.js` を差し込み、撮るループが毎コマ描かせる。

## 全体の流れ

1. リポジトリを調べる
2. 作り方を選び、設計の案を利用者に確かめる
3. 依存を入れ、エンジンを生成する
4. 最初の1場面を撮り、合格試験を通す
5. 動画のスキルを生成する
6. 利用者の台本で1本作り、合格試験を通す(4段で作った1場面が依頼の動画なら、飛ばす)
7. 利用者の指摘を、動画のスキルに書き足す

各段で、終わったと言える条件を満たしてから次へ進む。

## 1. リポジトリを調べる

次を調べ、結果を短くまとめる。コードを読めば分かることは、利用者に聞かない。

| 調べること | 調べ方の例 |
| --- | --- |
| アプリの起動のしかた | `package.json` のスクリプト、README。開発サーバーのポート |
| フレームワーク | React、Vue、Svelte、Next.js などか。ブラウザで動けばどれでもよい |
| ログインの有無 | 開発用の自動ログインがあるか。無ければ、Playwright のログインの状態の保存を使う |
| データの流れ | 画面がバックエンドから何で受け取るか。HTTP、少しずつ流す HTTP(Server-Sent Events など)、WebSocket |
| 部品にデータを外から渡せるか | 主な画面の部品が、データを props で受け取るか、部品の中で取りに行くか |
| 乱数や時刻を使う所 | `Math.random`、`Date.now`、`crypto.randomUUID` を画面の表示に使っているか |
| 遅延読み込みとフォント | `React.lazy` などの遅延読み込み、Web フォント |
| 既存のテストとビルド | Playwright が入っているか、本番のビルドの設定、テストの流し方 |
| 機微なデータ | 開発用のデータに、実在の人や会社の情報が入っていないか |

アプリを開発サーバーで起動し、Playwright で主な画面を開いて、通信の種類を見る。起動は止められる形(背景のタスク)で行う。ポートを指定してプロセスを止めない。ほかの作業の開発サーバーを止めうるからである。

## 2. 作り方を選ぶ

| | 画面の作り方(既定) | 部品の作り方 |
| --- | --- | --- |
| 映し方 | アプリの本物のページを開く。通信は録った応答を返し、時計を止め、決めたコマでクリックや入力をする。字幕、カメラは、ページの上に重ねる | アプリの部品を動画のページに並べ、値を props で渡して描く |
| 選ぶとき | ほとんどの場合。アプリのコードを変えずに済む | 部品がデータを props で受け取れる React のアプリで、画面に無い動きを細かく作りたいとき |
| 書き写す見本 | `references/samples/screen/` | `references/samples/component/` |

迷ったら画面の作り方を選ぶ。

設計の案を、利用者に確かめる。案には次を書く。

- 選んだ作り方と理由
- 生成するファイルの置き場。既定は `video/`(エンジンと場面の設定)と `.claude/skills/ui-video/`(動画のスキル)
- 入れる依存。Playwright と ffmpeg
- 最初の1場面の台本の案。どの画面で、何を打ち、何が起きるか。5〜10秒
- 本物の AI や外部のサービスに届く操作があるか。あれば、課金や送信が起きることを書く

利用者が確かめるまで、生成を始めない。依頼の中で「確認は不要」と言われていれば、案を短く書いて示し、そのまま進める。

## 3. 依存を入れ、エンジンを生成する

- Playwright を開発用の依存に入れ、chromium を入れる。どちらも、リポジトリのパッケージ管理のコマンドで行う(例: `pnpm add -D playwright` と `pnpm exec playwright install chromium`。リポジトリの上の階層にワークスペースがあり、そこに入ってしまうときは `--ignore-workspace` を付ける)。chromium の導入は、何も出力しないことがある。入ったかは、短いスクリプトで chromium を起動して確かめる。ffmpeg が無ければ、入れ方を利用者に伝える
- 選んだ見本を `video/` に書き写し、リポジトリに合わせて直す。見本の直し方の目安:
  - `apiPrefix`(録って返す HTTP の path の頭)と、WebSocket の URL の形を、アプリに合わせる
  - WebSocket を使うアプリは、場面の設定に `wsPattern`(録って返す WebSocket の URL の形)を書く。見本は、id で要求と応答が対応する形と、id が無く送った後に届いたものを応答とみなす形の、両方を返せる。ほかの形のときだけ `replay.mjs` を直す
  - 写した見本の冒頭の説明は、このリポジトリの言葉に直してよい
  - 文の言葉、字幕の大きさ、色を、利用者の好みに合わせる
- 見本にある、同じ絵にするための処理は消さない。乱数の固定、動きの同期、フォントと読み込みの待ち、毎コマ1回描かせる処理である。理由は `references/principles.md` の1節
- 録った通信の置き場(`video/recordings/`)と出力(`out/video/`)を `.gitignore` に入れる。既に入っていれば足さない
- 開発サーバーが、起動のときにファイルを作ることがある(Next.js の `AGENTS.md`、`next-env.d.ts` など)。自分が作ったものではないので消さず、利用者への報告に書く
- 場面の設定は `video/scenes/` の全部が合格試験の対象になる。案を比べるために設定を足すときは、同じ名前で録った通信も置くか、比べ終えたら消す。アプリを描く大きさを変えても、通信の中身が変わらなければ録り直さなくてよい
- 動画のコードを、本番のビルドに入れない。確かめ方:
  - 確かめは、合格試験の後にする。合格試験は開発サーバーを使い、フレームワークによっては、本番のビルドの前に開発サーバーを止める必要があるため
  - ビルドのスクリプトが `package.json` に無ければ、フレームワークのビルドのコマンド(例: `pnpm exec next build`、`pnpm exec vite build --outDir <一時の置き場>`)を使う
  - ビルドがあるアプリ: 本番のビルドを流し、出力を `__videoConfig` で探して、見つからないことを確かめる。例: `pnpm build && grep -rl "__videoConfig" <出力の置き場>/ || echo "入っていない"`。`replay` のような一般の言葉で探すと、フレームワーク自身のコードに当たる
  - Next.js のように、開発サーバーと本番のビルドが同じ置き場(`.next/`)を使うものは、開発サーバーを止めてからビルドする
  - ビルドの無いアプリ: 配っているフォルダ(`public/` など)を同じように探す

## 4. 最初の1場面を撮り、合格試験を通す

1. 場面の設定を書く。形は `references/samples/screen/shoot.mjs` の冒頭にある
   - 依頼の時点で台本と向き(横型か縦型か)が決まっていれば、最初の1場面はその台本で作る。この場合、この段で作った1場面が利用者の1本目になり、6段は飛ばして7段へ進む。5段(動画のスキル)は飛ばさない
   - 縦型は、場面の設定に `vertical` を書く。アプリはパソコンの大きさのまま描かれ、その絵が縦の台紙の窓に置かれ、字幕は台紙に描かれる。組み方の決まりは `references/principles.md` の7節の「縦型」
   - ボタンで送るアプリは、送るクリックに `send: true` を付ける
   - 強調の印、カーソル、題名の札、注記は、場面の設定の `marks`、`cursor`、`cards`、`notes` に書く。カーソルを着かせるコマは、クリックの操作と同じコマにする
   - 文の途中の語を丸で囲むと、前後の文字に線がかかり、合格試験の「線の重なり」で落ちる。文の1行や欄を枠で囲む
   - 効果音は `sounds` に書く。印やクリックに合わせて鳴らす音には `kind` を付けると、合格試験が時刻を突き合わせる
   - 字幕は操作の前に出す。録った応答はすぐ返るので、「更新中」のような途中の表示を見せたいときは `responseDelayFrames` で応答を遅らせる
   - 映したくない要素(クッキーの案内など)は `hide` に書く。フレームワークの開発用の表示は、既定で隠す
   - カメラの最初の寄る先は `{ full: true }` にする。画面の全体を、字幕の帯の下に収める。縦に長い要素に寄るときは `maxHeight` で上の部分に絞る
   - 流す応答の速さは、`stream` の操作の `every`(何コマに1つ渡すか)と `perFrame` で決める。文は録ったままにする
   - アプリが開いた直後に始める動き(一覧が下から出てくる、など)があれば、`leadFrames` で0コマ目の前に済ませておく
2. 画面の作り方なら、通信を録る(`record.mjs`)。本物の AI に届くなら、録る前に利用者に確かめる。録ったファイルに、鍵や個人情報が入っていないかを見る
3. 撮って mp4 にする(`render.mjs`)。コマを並べた画像を作って、自分の目で見る。並べ方の例: `ffmpeg -i out/video/frames/<名前>/%05d.png -vf "select='not(mod(n\,30))',scale=480:-1,tile=6x1" -frames:v 1 out/video/<名前>-sheet.png`。並べると文字が潰れる縦型は、窓の範囲を原寸で切り出して見る(`-vf crop=<幅>:<高さ>:<x>:<y>`)。並べた画像は `out/video/` に置く。見る点は次のとおり
   - 打った文字と応答の文が、録ったとおりに出ているか。文字が化けていないか
   - 字幕がアプリの大事な所を隠していないか。カメラが見せたい所に寄っているか
   - 読み込みの途中や、空の画面が映っていないか
4. 合格試験を流す。1本で数分かかるので、背景のタスクとして流す

   ```bash
   VIDEO_ORIGIN=http://localhost:<ポート> node <ui-video-builder の置き場>/scripts/check.mjs --adapter video/check-adapter.mjs
   ```

5. 「不合格」なら、生成した仕組みの側を直す。合格試験を書き換えて合格させない。「同じコマ」が合わないときは、`scripts/repeat.mjs` で同じコマを何回も撮って違う範囲を出し、`references/principles.md` の1節の表で原因を探す。カメラや字幕を試すときは `--check blank` や `--check safe` だけを流すと早い

終わったと言える条件: 合格試験が「合格」を出し、撮った動画を目で見て、上の3点に問題が無い。

## 5. 動画のスキルを生成する

`references/video-skill-template.md` のひな形を元に、このリポジトリ専用の動画のスキルを `.claude/skills/ui-video/SKILL.md` に書く。ほかのエージェント向けの置き場(`.cursor/skills` など)がリポジトリにあれば、その流儀に合わせる。

動画のスキルには、次を、このリポジトリの具体的なファイル名とコマンドで書く。

- 決まり。`references/principles.md` から、このリポジトリに当てはまるものを写す
- 置き場の表
- 「直したいこと → 変えるファイル → 一緒に直すもの」の対応表
- 手順。起動、録る、撮る、1コマずつ見る、合格試験、終え方
- 踏んだ落とし穴。生成の途中で踏んだものも書く

## 6. 利用者の台本で1本作る

利用者に台本を聞き、動画のスキルの手順で1本作る。横型 16:9 と、TikTok 向けの縦型 9:16 のどちらが要るかを聞く。縦型は、横型の絵を切り抜くだけではうまくいかない。組み方は `references/principles.md` の7節の「縦型」に従う。

できた動画を利用者に渡すとき、合格試験の結果と、目で見たコマの番号を添える。

## 7. 指摘を書き足す

利用者の指摘で直したことは、その場で動画のスキルの決まりか落とし穴に書き足す。日付と理由を添える。機械で判定できる決まりは、テストか合格試験に足す。

## してはいけないこと

- 合格試験(`scripts/check.mjs`)を書き換えて合格させる
- 画面を録画して動画にする
- 動画のために数値や AI の応答の文を手で書く
- 利用者に確かめずに、本物の AI や外部のサービスに課金される呼び出しを送る
- 録った通信を git に入れる
- 利用者に確かめずに、アプリの部品に動画のための分かれ道を足す
- 既にある mp4 や音声を、退避せずに上書きする

## 任意の機能: ナレーション

利用者が頼んだときだけ入れる。ElevenLabs を使い、鍵と声の id は利用者が用意する。

1. 場面の設定の `narration` に、発話の id、文、話し始めるコマ(`at`)か前の発話からの間(`after` と `gap`)を書く。読みを直すときは `say` に仮名の文を書く
2. 何本の発話を作るかを利用者に伝え、課金されることを確かめてから、`ELEVENLABS_API_KEY=... node video/narrate.mjs --video <名前>` を流す。文が前と同じ発話は作り直さない。前の音声は `before-<日時>/` へ移る
3. `render.mjs` が、発話の長さから時刻を決めて音声を重ね、発話の文で字幕の SRT を書く

注意は `references/principles.md` の8節にある。
